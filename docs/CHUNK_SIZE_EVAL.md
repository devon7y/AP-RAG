# Chunk-size & chunker-strategy evaluation

Empirical study to set AP-RAG's chunking parameters (`CHUNK_TARGET_TOKENS`,
`CHUNK_OVERLAP_TOKENS`) and to sanity-check the structure-aware scientific chunker
against generic baselines — using the **production Qwen3-Embedding-8B** embedder,
before committing to an expensive full reingest.

**Bottom line:** scientific chunker defaults lowered from **800/1000/300/150** to
**`512 / 640 / 192 / 51`** (target/max/min/overlap). The old 800/150 is too large
for retrieval on this embedder; 512 maximizes broad/conceptual recall and deep
retrieval while costing almost nothing on factual recall. Keep the scientific
chunker — it is competitive with (and on conceptual questions beats) the generic
fixed/recursive chunkers. Harness lives in [`scripts/chunk_eval/`](../scripts/chunk_eval/).

---

## Methodology

Chroma's *"Evaluating Chunking Strategies for Retrieval"* methodology: chunks are
treated as bounding boxes over the source, scored by character-span **Recall /
Precision / IoU** against a question's "golden" excerpt(s). One faithful
adaptation and one deliberate choice:

- **Production-faithful retrieval.** Chunks are embedded with the real
  **Qwen3-Embedding-8B (BF16)** on Fir, asymmetrically — questions get the
  `"Instruct: …\nQuery:"` instruction, chunks get none, `normalize_embeddings=True`
  — exactly as `pipeline/ingest.py` + `scripts/server.py` do. (This is why the
  official `chunking_evaluation` package can't be used as the engine: it embeds
  queries and documents symmetrically, and its char-span locator assumes chunks
  are raw substrings, which the furniture-stripping scientific chunker violates.
  We replicate its metric math and baseline chunkers instead; a `Locator` that
  whitespace-/case-normalizes with an index map back to source offsets generalizes
  Chroma's `rigorous_document_search` so the transforming chunker can still be
  scored — its locate-miss rate is ~1%.)
- **Contextualization OFF.** Identical for every chunker, so the comparison is
  fair. This *understates* production broad-question recall, because production
  prepends an LLM context blurb to each chunk (Anthropic contextual retrieval) and
  answers thematic queries through the knowledge graph — neither is scored here.
- **Two question types** (run 2): *factual* (one short verbatim excerpt — favors
  tight chunks) and *conceptual* (2–4 verbatim excerpts from different parts of the
  paper; golden = their union — favors chunkers that keep related evidence
  together). Synthetic QA generated by an LLM, every excerpt verbatim-validated.

### Pipeline (reproduce)

```bash
# 1. LOCAL — extract PDF text (matches ingest's pypdf + form-feed page joins)
python scripts/chunk_eval/extract_corpus.py --papers <DIR> --out scripts/chunk_eval/corpus.jsonl
# 2. LOCAL — synthetic QA (OPENAI_API_KEY stays local; gpt-5-mini, medium effort)
python scripts/chunk_eval/gen_questions.py --corpus …/corpus.jsonl --out …/qa.jsonl \
    --factual-per-doc 3 --conceptual-per-doc 3 --workers 8 --model gpt-5-mini
# 3. FIR — chunk × embed × retrieve × score on a MIG H100 (BF16)
sbatch --export=ALL,CORPUS=corpus.jsonl,QA=qa.jsonl,OUT=results.json slurm/job_chunk_eval.slurm
```

Grid: chunker ∈ {scientific, fixed, recursive} × size ∈ {128,192,256,320,384,512},
plus an overlap sweep {0,64,128} at size 256. Metrics at retrieval k=5 and k=10.

> **Ops note:** request the `nvidia_h100_80gb_hbm3_3g.40gb` **MIG slice**, not a
> full `h100:1` — the full-H100 request hit a `CUDA driver initialization failed`
> crash on a bad node and queued ~77 min; the MIG slice is reliable and schedules
> in minutes, and the 8B BF16 model fits its 40 GB.

## Run 1 — semanticfa corpus (factual only)

67 papers, 153 factual questions. Key results (Recall/IoU at k=5):

| config | mean_tok | R@5 | IoU@5 | R@10 |
|---|---|---|---|---|
| **fixed-256** | 254 | **0.718** | **0.021** | **0.855** |
| fixed-512 | 506 | 0.624 | 0.009 | 0.781 |
| fixed-800 | 786 | 0.648 | 0.006 | 0.844 |
| scientific-256 | 244 | 0.523 | 0.013 | 0.667 |
| scientific-512 | 382 | 0.536 | 0.007 | 0.686 |
| scientific-800 | 470 | 0.542 | 0.005 | 0.693 |

Findings: smaller chunks win on factual recall + IoU; **800 is too large**; overlap
gives no benefit (slightly hurts). The scientific chunker trailed fixed on
pinpoint retrieval — but a coverage-ceiling check showed it *contains* the golden
excerpt 97% of the time (≈ fixed's 100%), so the gap was a **ranking** effect on
pinpoint queries, not an exclusions/coverage problem. Caveat that drove run 2: a
factual-only question set is **biased toward small chunks**.

## Run 2 — CML/Caplan-lab corpus (factual + conceptual)

101 papers (sample of 161 valid PDFs), 374 questions = **222 factual + 152
conceptual**. Recall@5 by chunker × size (sweet spots **bold**):

| size | sci Rfact | sci Rconc | fix Rfact | fix Rconc | rec Rconc | sci R@10 | fix R@10 |
|---|---|---|---|---|---|---|---|
| 128 | **0.464** | 0.283 | 0.403 | 0.216 | 0.206 | 0.518 | 0.454 |
| 192 | 0.416 | 0.318 | 0.385 | 0.305 | 0.290 | 0.524 | 0.494 |
| 256 | 0.423 | 0.338 | 0.421 | 0.266 | 0.302 | 0.526 | 0.504 |
| 320 | 0.423 | 0.346 | **0.479** | 0.347 | 0.324 | 0.505 | 0.558 |
| 384 | 0.383 | 0.359 | 0.402 | 0.383 | 0.361 | 0.534 | 0.521 |
| 512 | 0.406 | **0.403** | 0.408 | **0.388** | 0.386 | **0.553** | **0.579** |

Best-in-class: factual recall → fix-320 (0.479), sci-128 (0.464); conceptual recall
→ **sci-512 (0.403)**; deep retrieval R@10 → fix-512 (0.579), sci-512 (0.553);
precision/IoU@5 → **sci-128 (0.032)**.

### Findings

1. **Factual and conceptual questions want opposite chunk sizes.** Factual recall
   peaks small–mid (≤320); conceptual recall climbs monotonically with size,
   peaking at 512 for every chunker. Run 1's "smaller is better" was a
   factual-only artifact.
2. **The scientific chunker is competitive — and wins where it should.** It is the
   single best config on conceptual recall (sci-512) *and* on precision/IoU
   (sci-128). Run 1's large fixed≫scientific gap was pinpoint-factual-only.
3. **Deep retrieval favors 512.** At k=10 (closer to how production retrieves),
   512 wins for all chunkers. **800 remains unsupported** — IoU keeps falling past
   512 with no recall payoff.
4. **Overlap hurts the scientific chunker** (sci-256 at overlap 0/64/128 →
   0.376/0.351/0.319); ~10% is the practical sweet spot. Large overlap on the
   fixed chunker buys marginal factual recall at 2× index size — not worth it.

## Recommendation & applied defaults

A single flat chunk size **cannot** maximize both factual and conceptual — that is
what the opposite gradients mean. Chosen for AP-RAG's profile (conceptual-leaning
academic Q&A, deep retrieval, KG construction, contextualization on):

| Param | Old | **New (applied)** |
|---|---|---|
| `CHUNK_TARGET_TOKENS` | 800 | **512** |
| `CHUNK_MAX_TOKENS` | 1000 | **640** |
| `CHUNK_MIN_TOKENS` | 300 | **192** |
| `CHUNK_OVERLAP_TOKENS` | 150 | **51** (~10%) |

Why 512: it gives up ≈0.02 factual recall vs smaller sizes while winning conceptual
recall and deep retrieval, suits the KG (coherent, section-respecting chunks) and
contextualization (fewer, richer chunks), and — for the scientific chunker — 512
dominated 384 on every recall metric at equal IoU. **Alternative:** if AP-RAG is
mostly pinpoint-factual lookup or answer-token cost is the priority, use
`256 / 320 / 96 / 0` (best factual + precision). The book chunker is unchanged.

Applied in: `pipeline/scientific_chunker.py` (`ChunkerConfig` + `from_env`), the
four `slurm/job_westbury_ingest_v2*.slurm` fallbacks, and `pipeline/ingest.py` +
`README.md` docs. Takes effect at the next reingest (chunk-size changes require
re-chunk + re-embed + re-extract).

### The "have both" path (future work)

To get peak factual *and* peak conceptual without compromise, use **small-to-big /
parent-child retrieval**: index small children (~256, factual precision) but return
their larger section parent (~conceptual context) at generation time. The chunker
already tracks section boundaries, so the parent is "the section this chunk came
from." Moderate engineering; composes with contextualization + the KG. Recommended
next step if factual precision proves weak in real use.

## Caveats

- Retrieval-only proxy (token-span overlap), **not** end-to-end answer quality, KG
  quality, or contextualized retrieval — all of which favor the scientific chunker
  and the larger end of the range.
- Differences among 256/384/512 are small and somewhat noisy (~0.03 recall on a
  few hundred questions); the *direction* (away from 800, toward ~512, low overlap)
  is robust, the exact number less so.
- Optimal size is corpus- and embedder-dependent; this answers it for academic
  papers + Qwen3-Embedding-8B.

## References (chunking literature consulted)

- Qu, Tu & Bao (2025), *Is Semantic Chunking Worth the Computational Cost?* Findings of NAACL 2025 — semantic chunking not worth the cost; structure-aware ≥ semantic.
- Smith & Troynikov (2024), *Evaluating Chunking Strategies for Retrieval*, Chroma — token-span IoU/Recall metrics; small chunks, zero overlap strong.
- Bhat et al. (2025), *Rethinking Chunk Size for Long-Document Retrieval* (arXiv:2505.21700) — larger (512–1024) wins on long-document/contextual QA.
- Wang et al. (2024), *Searching for Best Practices in RAG*, EMNLP 2024 — ~512 default + small-to-big.
- Sarthi et al. (2024), *RAPTOR*, ICLR 2024 — hierarchical/summary indexing for long docs.
- Anthropic (2024), *Contextual Retrieval* — prepend a situating blurb before embedding (already in AP-RAG).
